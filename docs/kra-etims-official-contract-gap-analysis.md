# KRA eTIMS official contract gap analysis

**Assessment date:** 27 October 2026  
**Scope:** existing Zoho Books sales fiscalization path and the checked-out, uncommitted `dev` tree. This is an evidence review only; no runtime behavior, mappings, gates, schemas, or provider calls were changed.

## Executive finding

The repository contains direct OSCU and VSCU protocol clients, a separate KRA sales mapper, durable submission attempts/payloads, and a reconciliation abstraction. The KRA adapters explicitly remain `contractVerified: false`, `operational: false`, and do not support reconciliation. This is appropriate: the available official contract documents are v2.0 from April 2023 and do not provide a seller-side status lookup or establish safe retry behavior after a possibly transmitted sale. The code's request validators and synthetic tests show local structural behavior only; they do not show KRA acceptance.

No sale submission should be activated from this assessment. The next safe step is to obtain the current contract and taxpayer-specific sandbox/certification package from KRA, then verify exact wire semantics and ambiguous-outcome handling in an approved sandbox before considering any production gate change.

## Reconciliation feasibility and outcome rules

Neither official OSCU nor VSCU v2.0 specification reviewed describes an operation that retrieves the result of a prior seller sales-save call by a stable client-supplied identifier. OSCU §3.2.1 and VSCU §3.2.1 catalogue sales save and purchase-sales search separately. The purchase-sales search is buyer-oriented, scoped with taxpayer/branch and a request timestamp; it is not a status query for the seller's earlier `/saveTrnsSalesOsdc` or `/trnsSales/saveSales` call. The documents do not guarantee that the search exposes all accepted sales, is immediately consistent, correlates to a local operation, or gives a final negative result.

Submitted trader/invoice numbers may assist a human investigation, but the specs do not establish them as idempotency keys, unique lookup keys, or guarantees that duplicates return the original receipt. A response code of `001` means no search result in the generic table; it is not documented as proof that a sales write did not commit. Communication/overlap codes likewise do not establish side-effect-free failure or recover the original response. A counter is not request-specific proof.

These are useful local audit/recovery records, not KRA acknowledgments. Do not invent a lookup endpoint or convert a missing record into permission to resubmit.

## Mapping and financial correctness risks

The mapper in `src/application/etims/kra-sales-mapping.ts` accepts explicit configuration and externally supplied calculation evidence. It does not compute taxes or rounding. It checks source ordering/identity, quantity and price agreement, tax bucket aggregation and selected total agreement, then emits schema fields. This is safer than inferring taxes, but it does not prove that the supplied calculation policy or field meanings match the current KRA contract.

## Purchase workflow boundary

Purchase submission is not part of the current Zoho Books outbound-sales fiscalization path. KRA purchase-related functions in the v2.0 material concern registering a taxpayer's purchases and searching supplier sales; they do not reconcile our own sale submission. A future workflow needs a separately scoped business process, appropriate supplier and buyer identity, purchase source-document data, item classification/units, purchase and tax amounts, receipt types/status, duplicate/idempotency semantics, authorization, persistence/audit history and a verified KRA contract. No purchase endpoint, application service, schema or UI is recommended in this feature.

## Missing evidence and recommended next step

Blocked evidence includes: current revision confirmation; taxpayer PIN/branch/device enrollment and permitted OSCU/VSCU mode; current VSCU package or OSCU credentials; official sandbox access and test data; exact HTTP/auth/request/response contract; current item/code data; approved calculation and sequence policy; code-specific rejection and duplicate semantics; and a written answer on seller-side recovery after a lost response. No live endpoints were called and no sandbox tests were run.

**Single recommended next step:** request a versioned, taxpayer-specific KRA integration acceptance pack before changing implementation. It must include the currently applicable specifications and package/API build, approved sandbox/onboarding access, assigned taxpayer/branch/device details, exact endpoint and auth schemas, code lists and field/financial policies, sequence ownership, result-code/duplicate side effects, and a supported post-timeout reconciliation/manual-resolution procedure.

Acceptance criteria for that pack and a subsequent sandbox phase:

1. KRA confirms the current applicable spec/build and taxpayer-specific authorization in writing.
2. Approved sandbox credentials and a dedicated test taxpayer/branch are provided without production access.
3. Exact initialization, reference-data, item, sales and receipt request/response models are captured and versioned; discrepancies between tables and samples are resolved.
4. Tax-inclusive/exclusive treatment, discount and rounding rules, receipt numbering, timestamps/timezone, buyer PIN and payment-code policy are signed off by KRA and the taxpayer.
5. KRA documents whether an accepted sale can be retrieved after response loss, the stable correlation key and lookup consistency/finality, and per-result-code/duplicate side effects. If no lookup exists, the approved manual path is explicit and automatic retries stay disabled.
6. Only after sandbox evidence is approved should a separate implementation proposal define narrowly scoped changes and safety tests. Production readiness additionally requires KRA vetting/certification and taxpayer sign-off.

## Verification and safety

This assessment reviewed existing documentation, code and test sources only. No tests, database checks, migrations, provider calls, invoice creation, or external submission operations were run. The supplied official PDFs and the KRA web page were read as documentation sources; the KRA service and taxpayer portal were not queried. Existing docs already contain the implementation inventory and mapping detail, so `docs/implementation-inventory.md` was not changed.
